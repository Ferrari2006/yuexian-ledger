## 二、网页操作步骤

1. 登录自己的GitHub账号，打开队长确认的团队仓库。
2. 本轮用户截图中的工作分支已建为`docs/platforms-operations`，继续使用该分支，无需因名称不同再建一个。一般情况下，有写入权限可在团队仓库创建分支，没有权限则先Fork；本轮按已建立的工作分支操作。
3. 确认当前是工作分支。进入`docs`目录，选择 **Add file → Upload files**，上传清单中的四份文档；预览中路径应以`docs/`开头。
4. 填写提交说明，例如“完善平台运营方案与统一实测执行材料”，提交到当前工作分支。
5. 回到同一工作分支的仓库根目录，更新`README.md`。如果远端已有其他更新，可使用文件编辑器仅合入运营方案入口这一处修改，预览后提交到同一分支。
6. 选择 **Compare & pull request**（或从 **Pull requests → New pull request** 进入）。核对目标仓库为`TinjiYDon/yuexian-ledger`，`base`默认选`master`（队长另指定时按其要求），`compare`是本次工作分支；从Fork提交时还要核对来源账号。
7. 检查 **Files changed**：应仅包含表中五份文档的预期变化。确认后点击 **Create pull request**，交由队长审查和合并。

分支保护和账号权限可能影响按钮是否可用。遇到无法提交时，先看页面原因，再由队长确认适合的协作方式。GitHub官方说明支持网页上传、新建分支与Pull Request协作，步骤可对照[上传文件说明](https://docs.github.com/en/repositories/working-with-files/managing-files/adding-a-file-to-a-repository)和[创建Pull Request说明](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request)。

## 三、建议的Pull Request内容

标题：完善赛题一平台运营方案与实测执行材料

正文：

> 围绕推广、拉新、激活和持续使用，明确目标用户与核心卖点，保留STP与4P分析，补充内容供给、主辅渠道选择、传播节奏、分角色激活和回访服务。首轮采用图文获客与社群承接，用母版、FAQ、集中答疑和同伴反馈控制投入，分别记录社媒表现、平台使用与实际工时。
>
> 实测排期服从官方统一安排，补充工时、指标、来源归因与复盘，并提供资源盘点、邀请、发布和记录模板。渠道资源尚未确认，方案与模板不代表已有执行结果。同步提交清单、README与网页提交说明，本次仅涉及文档。
>
> 指标按结果、过程、诊断三层组织，区分首次有效操作、获得承诺收益和后续使用；补充价值证据、确认覆盖、队列窗口及完整链路达成率。
>
> 按首个承诺类型比较价值达成，完善取数责任、缺失处理和暂停扩量规则；新增可填写的行为与汇总表、本地示范、首发文案及流程核验卡。核心材料仍待平台发布、图文排版和真实流程验证。
>
> 验证：本地检查文档链接、标题、表格结构与修改范围；用户访谈、渠道合作、平台能力验证和正式实测尚未完成。

## 四、怎样确认提交完成

- PR已创建：修改已交给团队审查，尚不代表已进入主分支。
- PR已合并：在团队目标分支打开方案与执行材料，检查内容、表格与链接，并确认主方案包含内容渠道、用户路径、实测执行和复盘章节。
- 若赛事要求在DataClawHub另交制品：按官方要求单独提交并核对回执，GitHub合并不替代赛事提交。

提交后记录PR链接与合并状态；赛事提交另记作品链接或回执。上传时只选择清单内文件，不需要上传整个项目目录。
