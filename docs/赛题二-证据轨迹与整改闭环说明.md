# 赛题二优化说明：证据轨迹与整改复检闭环

## 要解决的问题

原型已经能识别重量、柜封号和国家字段的矛盾，并给出“先别申报”的结论；但使用者看见风险后，仍会面临两个问题：

1. 不清楚数值从哪一站开始发生变化，无法快速核对责任环节；
2. 即使已确认应以哪份单据为准，也无法在同一流程中验证整改后能否申报。

本次优化将“发现问题”扩展为“定位证据—确认依据—整改复检—得到结论”的可演示闭环。

## 新增能力

### 1. 五站证据轨迹

对于每条阻塞规则，页面展示订舱、装箱单、提单、舱单、申报准备五个节点的字段值；首个发生变化的节点被明确标记。它回答的是“这个字段何时变了”，而不是只给出两个数值的静态差异。

### 2. 基于证据的整改选项

当重量、柜号或封条号不一致时，页面让使用者选择以哪份单据为依据；国家字段混填时，提供拆分字段的整改方式。每个选项都保留其业务含义，例如“以装箱单重量为准”。

### 3. 连续复检

每次选择整改依据后，系统仅在内存中生成该票货的新版本，并复用同一套规则再次判定：

`发现阻塞 → 选择依据 → 复检 → 仍有阻塞则继续整改 → 可以申报`

因此，一票货存在多个问题时不会因修复其中一项就被错误放行。原始样例数据不会被改写。

## 页面演示路径

以 `SH-2026-014` 为例：

1. 初始结果为“先别申报”，重量差异和国家字段混填均为阻塞项；
2. 通过重量证据轨迹确认装箱单为依据，选择“以装箱单重量为准”；
3. 系统立即复检，重量风险消失，但国家字段仍然阻塞；
4. 选择拆分国家字段后再次复检，最终显示“可以申报”。

这条路径可在离线生成的 `demo/index.html` 中直接操作，无需后端服务或网络连接。

## 实现与验证

实现集中在：

- `src/yuexian/rules.py`：生成字段轨迹、可选整改依据和整改后的样例副本；
- `src/yuexian/build_demo.py`：预计算每一步整改状态并生成可交互演示页；
- `tests/test_rules.py`：覆盖首个变更节点、原始数据不被改写、柜封号多来源整改，以及完整整改路径。

已通过 19 项自动化测试和提交前校验。判定仍由同一套确定性规则完成，浏览器只呈现预计算的结果，不在前端复制或绕过规则逻辑。

## 本次范围边界

本次只增强赛题二方向三的检查台，不修改赛题一的运营方案；不引入真实报关单据，也不把演示样例伪装为真实业务数据。后续接入真实单据时，可将抽取结果映射到现有字段轨迹和复检接口。
